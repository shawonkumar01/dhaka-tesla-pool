# Dhaka Tesla Pool

Share a seat. Split the fare. Survive Dhaka traffic.

**Live app:** https://dhaka-tesla-pool-eta.vercel.app/
**Backend API:** https://dhaka-tesla-pool-bxm4.onrender.com
**Repo:** https://github.com/shawonkumar01/dhaka-tesla-pool

> Note: the backend runs on Render's free tier, which spins down after ~15 minutes of inactivity. The first request after idle time can take 30–60 seconds to wake up — this is a free-tier trade-off, not a bug.

---

## 1. Summary & Problem Statement

Nusrat wants to get from Banani to Mohakhali. Rafiq wants to get from Banani to Gulshan 1 — a different but nearby destination. Jashim's Tesla, Bullet, has three seats. The app needs to figure out, in real time, whether strangers can share a ride, split the fare fairly, and track the trip through a clear lifecycle — while never overbooking a single seat, even when two requests land at nearly the same instant.

This is an MVP ride-pooling platform built around three actors — **Passenger**, **Driver/Vehicle**, and **Pool** — with a Node.js/Express backend, a Next.js frontend, and PostgreSQL, all containerized with Docker Compose and covered by an automated test suite.

## 2. Features Implemented

### Passenger

- Sign up / sign in (JWT auth, role-based)
- Request a ride: pickup zone, destination zone, seats
- See an estimated fare **before** booking, including whether a pooled discount is likely and whether any driver is currently available in that zone
- Track live status: `REQUESTED → MATCHED → ACCEPTED → DRIVER_ARRIVED → STARTED → AWAITING_PAYMENT → COMPLETED` (or `CANCELLED`)
- View ride history (all past and current rides)
- Cancel while the ride hasn't started
- Simulated payment: mark a completed trip as paid (cash or TeslaPay)

### Driver / Vehicle

- Sign in, go online/offline, set current zone
- Register a vehicle (name + fixed seat capacity) on first login if none exists
- See a proposed pool of passengers and explicitly **Accept** or **Decline** it
- Mark driver arrived → start trip → end trip → complete trip (gated on all riders having paid)
- See passengers, individual fares, and paid/unpaid status per rider
- View ride history

### Pool / Ride Split

- Multiple ride requests share one vehicle when pickup zones match and destinations are compatible
- Occupied seats never exceed vehicle capacity — enforced with a database row lock, not just application logic
- Each passenger gets an individually calculated fare (not a flat split)
- A vehicle runs one active pool at a time
- If a driver declines a pool, it's offered to the next eligible driver automatically, and that vehicle is never re-offered the same riders
- A vehicle's location updates to its drop-off zone after completing a trip, so matching reflects where the car actually is

## 5. Tech Stack & Justification

| Layer | Choice | Why |
|---|---|---|
| Frontend | Next.js (App Router) + Tailwind | Mandated recommendation; fast to build a clean UI without a design system |
| Backend | Express + TypeScript | Smaller surface area to fully own and defend than Nest/TypeORM, given the 1-day budget; every line is code we wrote, not generated by decorators |
| ORM | Prisma 5 | Schema-first, safe auto-migrations, full type safety; faster to a working migration + seed than TypeORM in this timeframe |
| Database | PostgreSQL | Relational integrity for capacity/pooling constraints; row-level locking (`SELECT ... FOR UPDATE`) is exactly what the concurrency problem needs |
| Auth | JWT (bcrypt-hashed passwords) | Stateless, no session store, simple middleware verification |
| Validation | Zod | Lightweight, composable, good error messages |
| Testing | Vitest + Supertest | Fast, modern, works well with TypeScript and a real Express app over HTTP |
| Hosting | Vercel (frontend) / Render (backend) / Neon (Postgres) | All genuinely free tiers; Vercel is purpose-built for Next.js, Render auto-deploys from GitHub, Neon's free Postgres doesn't spin down |

**What would make us switch later:** at real scale, Prisma's row-locking approach to concurrency would become a contention bottleneck — we'd move to a queue-based seat-reservation system (see Section 19, Bonus). Express's manual middleware wiring would benefit from Nest's structure once the team and codebase grow beyond a few developers.

## 8. Local Setup

### Prerequisites

- Node.js 20+
- Docker Desktop
- npm

### Quick start (Docker — recommended)

```bash
git clone https://github.com/shawonkumar01/dhaka-tesla-pool.git
cd dhaka-tesla-pool
docker compose up --build
```

This builds and starts Postgres, the backend (with migrations + seed data), and the frontend, all in one command. Once running:

- Frontend: http://localhost:3000
- Backend health check: http://localhost:4000/health

To reset to a clean, freshly-seeded state:

```bash
docker compose down -v
docker compose up --build
```

### Manual setup (without Docker)

```bash
# Backend
cd backend
cp .env.example .env   # fill in a local DATABASE_URL
npm install
npx prisma migrate dev
npx prisma db seed
npm run dev

# Frontend (separate terminal)
cd frontend
cp .env.example .env.local
npm install
npm run dev
```

## 13. Fare Model

All amounts are integer **poysha** (1 Taka = 100 poysha), avoiding floating-point rounding errors in money math.

baseFare = 3000 × seats
distanceCharge = distanceKm × 2000 × seats
poolDiscount = 20% of (baseFare + distanceCharge), only when pooled
finalFare = baseFare + distanceCharge − poolDiscount

Distance is the straight-line (Haversine) distance between hardcoded Dhaka zone coordinates, rounded to 0.01 km, with a 1.00 km minimum — no real routing, per the brief's guidance.

### Worked example — hand-checkable

|                         | Nusrat (Banani → Mohakhali) | Rafiq (Banani → Gulshan 1) |
| ----------------------- | --------------------------- | -------------------------- |
| Distance                | 1.80 km                     | 1.76 km                    |
| Base fare               | 3000                        | 3000                       |
| Distance charge         | 1.80 × 2000 = 3600          | 1.76 × 2000 = 3520         |
| Subtotal                | 6600                        | 6520                       |
| Pool discount (20%)     | 1320                        | 1304                       |
| **Final fare (pooled)** | **5280 (৳52.80)**           | **5216 (৳52.16)**          |
| Final fare (solo)       | 6600 (৳66.00)               | 6520 (৳65.20)              |

Run `npx tsx scripts/printFares.ts` from `backend/` to regenerate these numbers directly from the code.

Payment is simulated: cash or a TeslaPay wallet flag, no real gateway. A passenger marks their own completed ride as paid; the driver cannot complete the trip until every rider in the pool has paid.

## 14. Matching Rule

Two ride requests can share a pool if:

1. **Same pickup zone**, and
2. **Compatible destination zones** — identical, or on a hardcoded "nearby" list (e.g. Mohakhali ↔ Gulshan 1 ↔ Gulshan 2)

Full detail in [`docs/matching-rule.md`](./docs/matching-rule.md).

A new pool only opens on a vehicle whose `currentZone` matches the pickup zone — a driver on the other side of the city is never offered a mismatched pickup.

## 15. Concurrency: The Last-Seat Problem

**The scenario:** Bullet has one seat left. Nusrat and Shirin both request it at nearly the same instant. Both see "1 seat available" when they check.

**How this system handles it:** the seat-claiming logic runs inside a database transaction. Before writing anything, it takes a row lock on the specific pool (`SELECT ... FOR UPDATE`) and **re-checks capacity after acquiring the lock** — that re-check is the authoritative one, not the earlier optimistic read. PostgreSQL guarantees only one transaction can hold that lock at a time, so whichever request arrives first wins the seat; the second transaction blocks until the first commits, then sees the seat is already gone and falls through to "wait for the next opportunity" instead of double-booking. The same pattern (lock, then re-check) protects a vehicle from having two pools opened on it simultaneously.

This is directly verified by `tests/concurrency.test.ts`, which fires two requests with `Promise.all` and asserts exactly one wins and capacity is never exceeded.

**At larger scale**, row-level locking on a single Postgres instance becomes a contention bottleneck under heavy concurrent load on popular routes. We'd move to an idempotent, queue-based seat-reservation system (e.g. a Redis-backed distributed lock or a dedicated reservation service), so seat-claiming doesn't hold a database transaction open under load.

## 16. Key Decisions & Trade-offs

- **Extended lifecycle beyond the brief's suggestion.** The brief's `MATCHED/ACCEPTED` is one combined step; we split it into two (`MATCHED` = proposed, `ACCEPTED` = driver confirmed) because a driver who can't decline isn't a realistic dispatch flow, and the brief separately lists "accept a ride/pool" as its own driver capability. We also added `AWAITING_PAYMENT` before `COMPLETED`, so a trip can't be closed out until every rider has actually paid.
- **Decline → re-dispatch.** If a driver declines, the affected riders are immediately re-matched against other eligible drivers, and that vehicle is permanently excluded from being offered those same riders again (`PoolDecline`).
- **Vehicle zone tracking.** A vehicle's location updates to its last drop-off point on trip completion, not just wherever the driver manually set it — otherwise matching would use stale location data.
- **One active pool per vehicle.** A car can't run two simultaneous trips; the matching logic explicitly checks this before opening a new pool.
- **Money as integer poysha**, never floats, to avoid rounding drift in fare math.
- **Vehicle provisioning:** vehicles can come from seed data (the story cast) or self-registration by a driver with no vehicle yet.

## 17. Known Limitations

- If one rider in a pool cancels, the remaining rider(s) keep the pool discount they already had rather than it recalculating to a solo rate.
- Dispatch runs on specific triggers (new request, decline, cancellation, driver going online, trip completion) rather than a continuous background scheduler — sufficient for this MVP's scale, but would need a proper worker/queue at higher volume.
- Decline memory is per ride request, not per passenger — a passenger who cancels and re-requests could be offered to a driver who already declined their earlier request.
- The pre-booking "driver available" signal is a quick heads-up check, not the authoritative matcher — in rare cases it could say "available" moments before another rider claims the last seat.
- No rating or audit-log tables (explicitly optional per the brief).

## 18. Next Improvements

- Real-time updates via WebSockets instead of polling
- Rating system for passengers and drivers
- A dispatcher/admin view

## 19. Bonus: Scaling to 1M Passengers / 100k Drivers

Without over-building this MVP, here's how the architecture would need to evolve:

- **Load balancing & horizontal scaling:** the stateless Express API scales horizontally behind a load balancer trivially, since auth is JWT-based (no server-side session affinity needed).
- **Database:** the single Postgres instance becomes the bottleneck first. Read replicas for queries (fare estimates, history, availability checks) with writes staying on the primary; indexes already exist on `status` and `poolId` — at scale, add composite indexes on `(currentZone, isOnline)` for vehicle lookups.
- **Geospatial search:** the hardcoded zone list doesn't scale to a real city grid — this is where PostGIS or a dedicated geospatial index (e.g. Uber's H3) replaces the zone-matching logic entirely.
- **Concurrency at scale:** row-level locks on one Postgres instance won't hold up under heavy concurrent seat-claiming on popular routes — move to a distributed, idempotent reservation system (Redis-backed locks or a dedicated matching service) so a seat claim doesn't hold a DB transaction open under load.
- **Caching:** fare estimates and zone compatibility rules are cacheable (Redis) since they change rarely.
- **Queues/events:** dispatch (`dispatchWaitingRequests`) should move from synchronous in-request calls to an event-driven worker consuming from a queue (SQS/RabbitMQ), decoupling matching from the request/response cycle.
- **Real-time communication:** replace 4-second polling with WebSockets or Server-Sent Events for live ride/pool status.
- **Rate limiting & idempotency:** protect `/rides` (POST) with rate limiting per user and idempotency keys to survive client retries without duplicate bookings.
- **Observability:** structured logging, request tracing, and metrics on match latency, decline rates, and capacity-rejection rates — all currently invisible.
- **DB contention & retry strategy:** under high concurrency, expect lock-wait timeouts on hot pool rows; add exponential backoff and a circuit breaker around the matching transaction rather than letting requests queue indefinitely.
- **Security:** move JWT secret rotation, rate-limit auth endpoints against brute force, and add refresh tokens instead of long-lived 7-day access tokens.
- **Deployment strategy:** blue-green or canary deploys for the backend, since a bad matching-logic deploy could silently corrupt in-flight pools.

**One rejected/changed suggestion:** early on, when a real gap was found in the driver flow (drivers had no way to decline a proposed pool, and no re-dispatch existed for a declined pool), Claude's first suggestion was to simply _document it as an accepted limitation_ rather than build it. This was rejected — a driver being unable to say no isn't a realistic dispatch flow, and the brief's own driver capability list separately names "accept a ride/pool" as a feature. The fix was pushed for and implemented properly instead: an explicit `ACCEPTED` status, a decline endpoint, decline-memory (`PoolDecline`) so a vehicle is never re-offered riders it already turned down, and automatic re-dispatch to the next eligible driver.
